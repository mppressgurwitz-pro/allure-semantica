# Архитектура: двухкабинетная система управления карточками WB

**Дата:** 2026-05-21
**Статус:** черновик на согласование
**Автор:** агент M. (на основе работающего PUSH PGBOT1M08 → Асмус HTTP 200)

---

## 1. Цель

Обеспечить:
1. **Создание новых карточек** через мастер-файл одной кнопкой, с автоматической пропиской кабинета (Asmus/Quantum) и регистрацией в реестре.
2. **Управление кодом централизованно** — одна правка в Library мгновенно действует во всех 120+ карточках, без ручного апдейта каждой.
3. **Маршрутизацию PULL/PUSH** по кабинету — каждая карточка знает свой WB API ключ.
4. **Миграцию существующих 120 копий** на новую архитектуру без потери работающего потока.
5. **Базовый разбор проблемы Маши** с отсутствующей «волшебной палочкой» (отложено, не блокер).

## 2. Главное архитектурное решение

### Проблема
Bound script привязывается к Spreadsheet и при `File.copy()` копируется как независимая копия. Менять код в 120 копиях вручную невозможно. Это утверждение пользователя «один скрипт, изменяя который меняем всё» — фактически неверно для текущей модели inlined bound-script. Это надо честно зафиксировать.

### Решение: Apps Script Library + тонкие bound-wrappers

```
┌──────────────────────────────────────────────────────────────────┐
│                  WBSyncLib (Standalone Script)                    │
│                  Один проект, один scriptId                       │
│                                                                   │
│  • pullFromCabinet(cabinet)   • pushToCabinet(cabinet)            │
│  • flattenCard(json)          • mergeCard(existing, draft)        │
│  • fetchCardByVendorCode_safe(cabinet, vendor)                    │
│  • getApiKey(cabinet) → читает Script Properties                  │
│  • buildMenu(ui)              • registerNewCard(meta)             │
│                                                                   │
│  Script Properties:                                               │
│    WB_API_KEY_ASMUS    = "..."                                    │
│    WB_API_KEY_QUANTUM  = "..."                                    │
│    MASTER_FILE_ID      = "16OBo1En..."                            │
│    RESULTS_FOLDER_ID   = "1gDUCk2a..."                            │
└─────────────────────────┬────────────────────────────────────────┘
                          │
                          │  Library import (по scriptId)
                          ▼
┌──────────────────────────────────────────────────────────────────┐
│  В каждой копии Sheet — тонкий bound-script (~40 строк)           │
│                                                                   │
│  function onOpen() {                                              │
│    WBSyncLib.buildMenu(SpreadsheetApp.getUi());                   │
│  }                                                                │
│  function pullAsmus()    { WBSyncLib.pullFromCabinet('Asmus'); } │
│  function pushAsmus()    { WBSyncLib.pushToCabinet('Asmus'); }   │
│  function pullQuantum()  { WBSyncLib.pullFromCabinet('Quantum'); }│
│  function pushQuantum()  { WBSyncLib.pushToCabinet('Quantum'); } │
└──────────────────────────────────────────────────────────────────┘
```

**Эффект:**
- Меняем код в Library → все 120 копий следующим открытием получают новую версию.
- Никаких 120 копий кода. Никаких 120 апдейтов.
- Bound-wrapper меняется крайне редко (только если меняется состав меню).

**Цена решения:**
- Маша (и любой пользователь) при первом открытии Library должна **разово авторизовать scopes** (Spreadsheet, UrlFetch, Drive). Это, скорее всего, корень проблемы с «волшебной палочкой» — onOpen не выполнялся, потому что Library не была авторизована.
- Разовая миграция 120 существующих копий: их inlined-код надо заменить на тонкий wrapper через Apps Script REST API.

## 3. Маршрутизация по кабинету

### Способ 1 (основной): Реестр SKU в мастер-файле

Новый лист `Реестр SKU` в мастер-файле (https://docs.google.com/spreadsheets/d/16OBo1Enr19SFOuLm2pNy_JagMFppNqXKsYlUbLw_8S0):

| vendorCode | nmID | cabinet | sheetId копии | URL | создано | последний sync | статус |
|------------|------|---------|---------------|-----|---------|----------------|--------|
| PGBOT1M08  | 891058906 | Asmus | 1NOO50oa9CWfXzA7AixR7zapj1xzr2e3xhK7lM6Cc3bQ | … | 2026-05-19 | 2026-05-21 14:32 | OK |
| QNT-XXXX-01| …        | Quantum | …            | …   | …        | …              | … |

Library при PUSH/PULL:
1. Читает vendorCode из активного листа карточки.
2. Лезет в Реестр SKU мастер-файла, находит строку, берёт `cabinet`.
3. Достаёт нужный ключ из Script Properties.
4. Действует.

### Способ 2 (fallback, если карточка ещё не в реестре): шапка листа карточки

В `_Advice_SEO_Draft` ячейка `B1` = `Asmus` или `Quantum`. При создании копии скрипт прописывает её автоматически. Если Реестр недоступен — Library читает шапку.

### Меню в каждой копии

```
🪄 SEO в WB
   ├── 📥 Загрузить из WB (PULL)
   │     ├── Из Асмус
   │     └── Из Quantum
   ├── 📤 Выгрузить в WB (PUSH)
   │     ├── В Асмус
   │     └── В Quantum
   ├── ─────────────
   ├── 📊 Открыть мастер-файл (Реестр)
   └── ⚙️ Ozon (скоро) — disabled
```

Кнопка PULL/PUSH **не предполагает выбор кабинета** в диалоге — кабинет берётся из реестра. Если реестр недоступен и шапка пустая — UI спрашивает один раз, фиксирует в шапке и в реестре.

```
    ▼
[WB API]
    │  HTTP 200 → отметка в Реестре «последний sync» + статус OK
    │  HTTP 400/500 → отметка с ошибкой
    ▼
[Готово]
```

## 5. Миграция 120 существующих копий

**Не делать руками. Скриптом, единожды, с dry-run.**

```
Шаг 1. Discovery
  • DriveApp.getFolderById(RESULTS_FOLDER_ID).getFiles() → собрать список
  • Для каждого: открыть, прочитать B1/vendorCode/nmID
  • Заполнить Реестр SKU (cabinet проставить = 'Asmus' для всех, потом
    при необходимости Маша вручную переключит несколько на Quantum)

Шаг 2. Найти scriptId каждой копии
  • Apps Script REST API: GET /v1/projects?filter=type=BOUND&parentId={fileId}
  • Записать scriptId в служебную колонку Реестра

Шаг 3. Dry-run на 1 копии
  • Выбрать тестовую (не PGBOT1M08! — другую, заранее непродуктивную)
  • projects.getContent → сохранить backup
  • projects.updateContent с новым тонким wrapper
  • Открыть, проверить: меню появляется, PULL работает

Шаг 4. Массовый прогон
  • Для каждой копии: backup → updateContent
  • Логирование каждого шага в Реестр (колонка "миграция")
  • Откат: если 3 копии подряд упали — стоп

Шаг 5. Smoke-тест регрессии
  • PGBOT1M08 → PULL → PUSH (должен быть HTTP 200, как 2026-05-21)
```

**Риски миграции:**
- Apps Script API требует включённого Apps Script API в Google Cloud Console + scope `https://www.googleapis.com/auth/script.projects`.
- В копиях могут быть посторонние правки (Bootstrap.gs пользовательский). Backup обязателен.
- Маша должна перелогиниться после миграции, иначе старая авторизация может конфликтовать.

## 7. Проблема Маши (диагностика)

Симптом: в копии мастера у Маши нет «волшебной палочки» (custom menu).

Гипотезы по убыванию вероятности:
1. **onOpen у Маши не выполнился из-за отсутствия авторизации Library scopes.** Маша — не владелец, Library требует индивидуальной авторизации первый раз. Лечение: добавить инструкцию + при первом открытии Library покажет диалог авторизации.
2. **Маша не имеет прав Editor на Library script.** Лечение: дать ей роль Editor через Drive Permissions.
3. **Bound script не скопировался при File.copy().** Маловероятно — Google копирует bound с файлом.
4. **Маша открывала файл в режиме View / в режиме без подключения к Apps Script** (например, через mobile или embedded preview). Лечение: открывать только через docs.google.com на десктопе.

**Что я заложу в Library для самодиагностики:**
- `diagnoseAccess()` — функция в меню «🔧 Диагностика», которая логирует email текущего пользователя, права на Library, права на мастер, версию Library. Маша запустит — пришлёт скриншот.

## 10. Критические возражения к этому плану — где он может развалиться

Честно перечисляю слабые места:

1. **Apps Script Library добавляет latency при каждом вызове.** Это ~200ms на функцию. На PUSH одной карточки незаметно, но если хочется batch-прогон 120 SKU — суммарно полминуты только на накладные. Mitigation: batch-функции делать на стороне Library, не дёргать её в цикле из bound.

2. **Library версионируется.** Если ты её правишь и забываешь поднять версию + переподключить в копиях на `HEAD` — копии могут крутить старую версию. Подключим на `Development mode` (HEAD), чтобы изменения шли мгновенно. Но это означает: правка Library мгновенно влияет на боевые карточки. Это и плюс, и минус — ошибиться можно дорого.

3. **Миграция 120 копий — самая опасная операция.** projects.updateContent перезаписывает весь код. Если backup сломан и я неправильно собрал wrapper — потеряем правки, которые могла внести Маша или ты в отдельных копиях. Перед массовым прогоном — backup в Drive в виде .gs файлов.

4. **Маша может не иметь прав на Apps Script API.** Для триггера onOpen ей хватит её авторизации, но для обращения к Реестру SKU в мастер-файле через Library — Library должна иметь Editor на мастер. Это решается scope, не правами Маши, но надо проверить.

5. **Если cabinet поле в B1 кто-то очистит** — Library должна гракефулно упасть в Реестр, иначе случайно отправим карточку Quantum в Асмус и затрём чужие данные. Защита: всегда PUSH делать с `vendorCode + cabinet` парой, и если cabinet не определён — отказ с громким диалогом, не дефолт на Асмус.
