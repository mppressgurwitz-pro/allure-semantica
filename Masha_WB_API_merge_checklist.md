# Чек-лист для Маши: как не дать WB обнулять ТНВЭД и декларации

**Дата:** 2026-05-20
**Цель документа:** убрать первопричину обнуления `тнвэд`/`сертификаты`/`декларации`/`габариты` при `uploadSelectedToWB`. Шаблон с правильными именами эту проблему сам по себе не решает — это решает merge в скрипте.

---

## Что происходит сейчас

При вызове `PUT https://content-api.wildberries.ru/content/v2/cards/update` (или `/cards/upload` для новых) WB **заменяет все характеристики карточки** на то, что пришло в теле запроса. Это не «patch», это «replace». Если в теле нет поля `тнвэд` — оно станет пустым. Если нет `габаритов` — обнулятся.

Поэтому правильный паттерн всегда: **GET → merge → PUT**. Никогда не PUT без GET.

---

## Правильный алгоритм `uploadSelectedToWB`

```
1. Из таблицы возьми артикул WB (nmID).
2. GET /content/v2/get/cards/list — забери ТЕКУЩУЮ карточку целиком.
   Body: { "settings": { "cursor": { "limit": 1 }, "filter": { "withPhoto": -1, "objectIDs": [...], "textSearch": "<nmID>" } } }
   Из ответа возьми объект cards[0].
3. Положи cards[0] в локальную переменную card.
4. Сделай deep copy: const merged = JSON.parse(JSON.stringify(card)).
5. Пройдись по новому _Advice_SEO_Draft. Для каждой строки, у которой сотрудник НЕ отметил "не изменять":
     a. Найди в merged.characteristics элемент с charcID, соответствующим имени из строки.
        Если такого charcID нет в карточке — найди по name (точное совпадение).
        Если и по имени нет — пропусти (значит, поле не относится к этой категории; в этом случае скрипт должен залогировать "skipped: <name>").
     b. Замени merged.characteristics[i].value на значение из таблицы.
6. Базовые поля из красного блока шаблона:
     - tnvedID → merged.tnvedID
     - дimensions (length, width, height) → merged.dimensions
     - characteristics с charcID для "Состав", "Назначение косметического средства", "Объем товара" — это нормальные characteristics, обработаны в шаге 5.
     - Декларации/сертификаты — это поле merged.documents (если есть в ответе) или отдельный endpoint, см. ниже.
7. Не трогай в merged: brand, nmID, vendorCode, sizes, photos, video.
   Эти поля управляются другими endpoints WB; PUT cards/update их не трогает, но если ты их не пришлёшь — WB на некоторых версиях API может ругнуться.
   Безопасный путь: оставить их в payload как пришли в GET.
8. PUT /content/v2/cards/update с merged в теле.
9. Сверь статус 200 + повторный GET через 10 секунд: проверка, что характеристики из шаблона легли, а tnvedID, dimensions, certificates НЕ изменились.
```

---

## Поля, которые обязаны быть в PUT (иначе обнуление)

Из ответа `GET /cards/list` для **каждого** PUT переноси:

| Поле | Тип | Почему |
|------|-----|--------|
| `nmID` | int | идентификатор карточки |
| `vendorCode` | string | артикул продавца |
| `brand` | string | бренд (некоторые версии API ругаются, если пусто) |
| `title` | string | наименование |
| `description` | string | описание |
| `tnvedID` | string | ТНВЭД-код (твой кейс с обнулением!) |
| `dimensions` | object {length, width, height, weightBrutto} | габариты |
| `characteristics` | array | все WB-характеристики |
| `sizes` | array | размеры/баркоды |
| `photos` | array | URL фото |
| `video` | string | URL видео |
| `subjectID` | int | категория WB |
| `width`, `height`, `length` | int | дублирующие габариты для совместимости |

Если в карточке есть `documents` (декларации/СГР) — этот объект тоже надо переносить. На некоторых аккаунтах WB возвращает их в `getCardsList` отдельным полем, на других — внутри `characteristics` с особыми charcID (`Номер декларации соответствия` и т.д.).

**Правило большого пальца:** всё, что пришло в GET и не помечено к замене — пиши обратно в PUT 1-в-1.

## Список характеристик категории "Пилинг" (для теста)

После GET для `nmID=891058906` ты должна увидеть `subjectName="Пилинг"` или `subjectID` категории Пилинг. Тогда в `characteristics` ожидаются 12 имён:

1. Вид пилинга
2. Действие
3. Комплектация
4. Назначение косметического средства
5. Объем товара
6. Особенности косметики
7. Срок годности
8. Страна производства
9. Торговое наименование
10. Упаковка
11. Форма упаковки
12. Формат пилинга

Если в GET пришли все 12, а в твоём шаблоне (любого варианта A/B/C) тоже 12 (или подмножество для редактирования) — всё верно. Если в GET пришло меньше, или другие имена — значит, у тебя `subjectID` другой; уточни у Михаила, возможно категория проставлена в WB не «Пилинг».

## Как проверить, что merge сработал

После `uploadSelectedToWB`:

1. Сделай GET через 10–30 секунд (WB кэширует).
2. Сравни `dimensions`, `tnvedID`, `documents` (если есть) с тем, что было до PUT.
3. Если значения те же — merge ок.
4. Если пусто — merge порушен.

Для прозрачности добавь в скрипт лог:

```
[uploadSelectedToWB] nmID=891058906
  GET before: tnvedID="3304990000", dims=15×12×10×280, certs=2
  PUT body: characteristics replaced=12, base preserved=tnvedID, dims, certs (2)
  GET after: tnvedID="3304990000", dims=15×12×10×280, certs=2 ✅
```

Если after≠before по базовым полям — merge ломается. Чини шаг 5–7.

---

## Что НЕЛЬЗЯ делать (повторение прошлой ошибки)

- **Нельзя** строить body PUT с нуля только из таблицы. Так было раньше — отсюда обнуление.
- **Нельзя** мапить имена по «похожести» (например, `Объём` → `Объем товара`). Если имя из таблицы не в charcs категории — пропускай и логируй, не угадывай.
- **Нельзя** убирать из PUT поля, которых не было в таблице. Они должны быть взяты из GET.
- **Нельзя** PUT-ить, если предыдущий GET не успел вернуться (бывает на медленном сетевом канале — добавь await).
